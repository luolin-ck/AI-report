### 数据采集 / RAG

- **搜索 API 正成为 agent 的决策界面。** arXiv 论文 *Equal Accuracy, Unequal Evidence* 对 Brave、Tavily、Firecrawl 进行同一 agent 策略下的对比，结论不是谁“绝对更准”，而是不同搜索面会改变 agent 的证据预算和继续探索行为。对 RAG 产品的启发是：评估搜索工具时要看“是否给出足够证据让 agent 决定打开页面”，不能只看最终答对几题。
- **Agent-first Web 讨论升温。** *Towards an Agent-First Web* 提出 agent 访问权、agent 标识、agent 优化内容、token 计费和内容溯源等原则。对 Firecrawl/抓取类工具而言，这意味着长期价值会从“绕过页面复杂性”转向“在合规识别、速率限制、可引用证据和变更监控下稳定采集”。
- **Web agent 安全建议倾向 plan-then-execute。** *Web Agents Should Adopt the Plan-Then-Execute Paradigm* 指出 ReAct 在网页环境中容易让未信任页面内容影响下一步动作；预先生成计划再执行，可减少页面 prompt injection 重写任务的机会。RAG/抓取链路如果要让 agent 自动点击、登录或写入，应该先固定工具图和可执行动作，再让网页内容只填参数。

## 今天值得深入研究的 1 个主题

**主题：把“AI 设计生成”从 prompt 试错升级为可审计的 design skill。**

建议研究路径：

1. 拆解 `Nutlope/hallmark`、`pbakaus/impeccable`、`google-labs-code/stitch-skills` 这类项目如何表达设计偏好、反例和检查项。
2. 为自己的产品建立一份 `design.skill.md`：包含品牌词、布局密度、组件半径、颜色禁区、动效节奏、图标规则、按钮文案、空状态和移动端约束。
3. 在 Codex/Claude Code/Cursor 中跑同一页面任务，对比“无 skill”和“有 skill”的首轮输出、返工次数、可访问性问题、响应式问题和组件复用率。
4. 把结果沉淀为团队模板，不要只存 prompt；要和设计系统、代码组件、截图验收和人工评审绑定。
