## 今日最值得关注

今天的主线是：Agent 开始从“预先塞入所有工具”转向“按需发现工具”，同时桌面 computer use、真实代码画布、抓取本地化和生产级生命周期钩子一起补齐执行层。对团队最有价值的动作不是再换一次模型，而是重新设计工具目录、权限边界、上下文预算和可验证回路。

### 1. Gemini API 推出 Tool Retrieval：大型工具库不再全部挤进上下文

- Google 11 月 19 日在 Gemini Interactions API 预览 Tool Retrieval。Agent 只先看到工具名称和描述，需要时再加载完整参数 schema；服务端模式无需自行建设索引，也支持远程 MCP server 的工具按需加载。
- **影响判断**：这是 50—数千工具场景的结构性优化，直接作用于输入 token、延迟、前缀缓存稳定性和工具选择准确率。
- **行动建议**：先把低频工具设为 `defer_loading: true`，保留高频工具常驻；以真实任务对比 token、延迟、误选率和权限过滤效果。
- 来源：[Google 官方发布](https://blog.google/innovation-and-ai/technology/developers-tools/gemini-api-tool-retrieval/) · [Gemini API 文档](https://ai.google.dev/gemini-api/docs/interactions#tool-retrieval)

### 2. Gemini for Mac 上线后台 computer use，桌面 Agent 进入普通用户工作流

- Gemini for Mac 可在隔离后台窗口中跨本地文件、桌面应用和网页执行多步任务；用户可选择应用权限、查看实时预览、暂停并批准关键动作。首批面向美国英语用户、Apple Silicon 与 macOS Sequoia 15.0+，需 Google AI Plus、Pro 或 Ultra。
- **影响判断**：桌面自动化从开发者专用 harness 进入消费级助手，但授权、敏感输入和不可逆操作仍是落地门槛。
- **行动建议**：只用低风险、可回滚任务试点，如批量整理素材或汇总仪表盘；为外发、付款、删除和发布保留人工确认。
- 来源：[Google 官方发布](https://blog.google/innovation-and-ai/products/gemini-app/computer-use-mac/)

### 3. AWS AgentCore harness 加入 Strands 默认能力与生命周期钩子

- AWS 11 月 19 日宣布 AgentCore harness 采用开源 Strands harness 默认能力，加入提示缓存、主动上下文管理、规划、网页检索、文件访问、上下文卸载和子任务委派；四类 lifecycle hook 可在调用前后或工具执行前后运行确定性允许/拒绝逻辑。
- **影响判断**：生产 Agent 的竞争点正在从“能调用工具”转向“默认可运行、可审计、可限制、可长期执行”。
- **行动建议**：固定安全边界的应用不要使用动态扩展的 `allowedTools: ["*"]`；显式列出工具，并为高风险动作设置 fail-closed 的 `before_tool_call` 检查。
- 来源：[AWS 官方发布](https://aws.amazon.com/blogs/machine-learning/amazon-bedrock-agentcore-harness-adds-strands-harness-defaults-built-in-tools-and-lifecycle-hooks/)

### 4. Firecrawl 同时押注本地抓取与 3,300+ 数据工具分发

- Firecrawl Local 以 Rust 重建本地 scrape / crawl / map 原语，官方称相对其自托管版本快 37 倍、空闲内存仅 11 MB（低 230 倍），并兼容现有 MCP 与 SDK；11 月 19 日又把 3,300+ 数据工具、专业索引和实时 Web 接入 Grok Bot marketplace。
- **影响判断**：一端是本地、低资源、可控的数据采集，另一端是大工具目录的分发；两者都指向 Agent 数据层从单一 Web scrape 扩展为多索引、多供应商路由。
- **行动建议**：本地或隐私敏感场景优先测 Firecrawl Local；官方 37×、230×和 Grok 插件“质量提升 21%”均为厂商口径，必须用自己的站点和问题集复测。
- 来源：[Firecrawl Local](https://www.firecrawl.dev/changelog/firecrawl-local) · [Grok Bot 插件](https://www.firecrawl.dev/changelog/grok-bot-mcp) · [Firecrawl Changelog](https://www.firecrawl.dev/changelog)

### 5. Onlook 重构为开源 agentic design tool，设计直接发生在真实代码上

- Onlook 把无限画布叠在本地真实代码库上：多个 worktree 可并行探索，每个画面是真实 webview，Claude Code 或 Codex 直接修改项目，结果以正常 git diff / PR 交付。项目采用 Apache-2.0，GitHub 当前约 27.4k stars。

- **行动建议**：拿一个 Next.js / React 内部工具做试点，重点验证多页面状态、设计系统约束、worktree 资源占用和 PR 可读性。
- 来源：[Onlook GitHub](https://github.com/onlook-dev/onlook) · [Launch HN 讨论](https://news.ycombinator.com/item?id=50562320)

## 分领域进展

### 设计生成

- **Onlook**：从传统可视化编辑器重构为 agentic design tool，核心差异是“真实代码 + 多 worktree + 无限画布 + 自带 Agent 账户”，适合设计工程协作和多方案并行探索。
- **Figma 多候选生成**：一次 prompt 直接比较多张图或多个模型，降低反复提示成本；更适合情绪板、封面草案和营销素材发散，不替代品牌审查。
- **Gemini for Mac**：官方示例包括批量调色和搭建 3D 场景，说明 computer use 正进入创意软件；由于当前仅有限地区/套餐可用，应先观察稳定性和权限体验。

### 数据采集 / RAG

- **Firecrawl Local**：本地 Rust 原语把抓取、爬取和站点映射下沉到设备，适合内网、低延迟或希望减少云端数据外发的场景；浏览器兼容、反爬覆盖和复杂页面准确率仍需实测。
- **Firecrawl Grok Bot 插件**：把 3,300+ 工具与专业索引打包为 Agent 可用入口，价值在 provider waterfall 与数据类型覆盖；厂商“答案质量提升 21%”缺少本次简报可独立复算的实验细节。
- **SageMaker 推理持续优化**：AWS 同日上线对 vLLM GPU endpoint 的延迟漂移、闲置 GPU 和配置缺口监控；它只看运行信号，不读请求/响应，生产变更仍需用户主动应用。[官方说明](https://aws.amazon.com/blogs/machine-learning/amazon-sagemaker-ai-now-detects-latency-drift-idle-gpus-and-missed-optimizations-on-your-inference-endpoints/)

### Agent 工作流

- **Tool Retrieval**：把“列出全部 schema”变为“工具名称/描述常驻、schema 按需加载”，并能对接远程 MCP server；这是今天最值得工程验证的变化。
- **AgentCore lifecycle hooks**：确定性策略可以在模型调用与工具执行边界生效，且对子 Agent 的工具调用同样适用，降低委派绕过策略的风险。
- **桌面 computer use**：Gemini 在隔离窗口运行、不占主屏鼠标，并把权限、预览、暂停和关键动作审批放进产品界面；可用性提升同时也扩大了本地数据面。

### 热门应用

- **Gemini for Mac computer use**：值得小范围试用，尤其适合跨 PDF、网页、表单和演示文稿的机械工作；不建议一开始就授权邮件群发、支付或公开发布。
- **Onlook**：值得设计工程团队复盘。它把设计探索、真实运行状态和可审查代码放在同一画布，比单向 design-to-code 更接近持续协作。
- **Figma 多模型图像候选**：适合需要快速发散的品牌、营销和产品团队；价值主要是减少重新提示次数，而不是自动决定“最好”的视觉方案。

## 今天值得深入研究的 1 个主题

### 从“工具目录”升级为“工具控制面”

Tool Retrieval、Firecrawl 的 3,300+ 工具、MCP Skills 和 AgentCore hooks 共同暴露出一个新问题：工具越多，真正的瓶颈越不是“能不能接入”，而是“何时让模型知道、允许谁调用、按什么成本加载、如何审计结果”。

建议做一个四层实验：

1. **发现层**：只常驻名称与描述，schema 按需加载；测试召回率与误选率。
2. **权限层**：按用户、组织和任务过滤可发现工具，避免“看得见但不该调用”。
