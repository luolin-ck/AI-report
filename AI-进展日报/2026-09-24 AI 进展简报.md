### Agent 工作流

- **混合本地/云端 Agent：** Antigravity SDK 的参考架构让云端模型仅依据文件名与任务描述制定计划，本地模型读取源码、修改并运行测试。官方演示报告 95 个云端 token、3,322 个本地 token，即 97.2% token 留在本地；这是厂商单次演示，不是通用性能基准。[官方说明](https://developers.googleblog.com/introducing-support-for-local-ai-models-in-the-antigravity-sdk/)
- **上线后 Agent：** Cursor Rollouts 读取 PR diff 自动生成监控计划，连接观测平台后比较发布前后指标，并可提醒、暂停渐进发布或提出回滚。它最适合有成熟指标和 feature flag 的团队；缺乏可靠基线时，Agent 只会放大错误告警。
- **最小权限 Agent：** GitHub Copilot 本地沙箱把目录、网络和凭据政策放入项目设置，并采用 fail-closed。建议把写权限限定到工作区，把外联限定到依赖源和业务所需域名，再逐步放开。

## 今天值得深入研究的 1 个主题

### Agent Harness 正在取代“单模型比较”，成为真实生产力差异

今天多条更新看似分散，实际都在补同一套生产系统：Cursor 优化系统提示词、工具加载、缓存与子 Agent；Antigravity 把云端规划与本地执行拆开；GitHub 把文件、网络和凭据政策做成 fail-closed 沙箱；Cursor Rollouts 又把 Agent 延伸到上线后的监控和回滚。模型仍重要，但成本、成功率和风险越来越由 harness 决定。

建议用一条真实任务建立四层评测：① 模型是否完成任务；② 工具与上下文消耗多少；③ 权限是否最小且失败可关闭；④ 上线后是否能发现回归并回滚。只看代码生成正确率，会漏掉后面三层，而这三层恰恰决定 Agent 能否进入生产。
