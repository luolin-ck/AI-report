## 分领域进展

### 设计生成

- Figma 最近的 release notes 指向一个清晰趋势：AI 生成不再只停留在画布草图，而是要把 Make 预览、MCP 生成代码、Chrome 捕获页面转成可编辑图层，并自动绑定颜色、字体和间距变量。2026-07-24 的 Auto Layout 更新也在拉近 Figma 与 CSS 布局模型的距离，旧 frame 需要主动迁移，新 frame 默认使用新版行为。
- Figma AI 的商业化信号增强。MarketWatch 报道称 Figma Q2 revenue 为 3.701 亿美元，同比增长 48%，design agent 已被超过半数 high-revenue customers 使用，但 AI 相关投入也推高亏损。对团队的现实含义是：试点 AI 设计工具时不要只看生成速度，还要看 AI credit 成本、设计系统一致性、变量绑定、handoff 到代码后的维护成本。
- OpenDesign 仍是值得跟踪的本地优先设计生成方向。它定位为 open-source vibe design workspace，可把本地 coding agent 转为设计引擎，支持多 agent、多设计系统、Figma export 和代码仓库工作流。最近可验证的公开发布节奏是 2026-07 的 0.13/0.14 系列，今天未核验到更新版本，因此不把它列为 48 小时内新版，只作为设计到代码/代码到设计方向的持续观察对象。
- Claude Design 相关 YouTube 教程仍在扩散，但本轮未发现官方新版。公开视频中“避免 AI slop”“让 Claude 成为 senior designer”“Figma + Claude workflow”等主题有较高可见播放量，说明设计团队正在寻找更可控的 prompt、审美标准和设计系统约束。

### 数据采集 / RAG

- Firecrawl v2.11.0 的 Research Index、keyless access、自动 PII redaction、deterministicJson、video discovery 和 web-scale monitor，把“抓页面”扩展到“持续监控、去重、结构化、隐私处理”的数据管线。对 RAG 来说，最值得验证的是 monitor 的告警去重、PII redaction 对下游召回的影响，以及 deterministicJson 是否能降低索引漂移。
- Fire-PDF / PDF Inspector 继续解决 PDF 入库的成本问题。官方博客称 Fire-PDF 面向混合、扫描和文本 PDF 输出结构化 Markdown，npm 页面显示 `@firecrawl/pdf-inspector` 版本为 1.11.1，可快速判断页面类型并减少不必要 OCR。适合用于合同、研报、手册、白皮书等 PDF 密集型知识库的预处理。
- GitHub Trending 中 Firecrawl、Bright Data CLI、MediaCrawler、code-graph-rag 等项目同时出现，说明“网页/社媒/代码库数据采集 + RAG”仍是开发者高频需求。注意：Trending 的“stars today”是 GitHub 页面口径，不等同于独立统计的净增长，需要和 repo 活跃度、issue 质量、许可证一起判断。

### Agent 工作流

- Muse Glimmer 是本轮最明确的官方模型事件。Meta 的定位不是通用聊天模型，而是本地 agent：工具调用、本地 coding、LLM-as-judge、长任务、失败恢复、消费级硬件部署。Ollama 已给出本地运行入口，并提到可为 Codex、Claude Code、OpenCode、GitHub Copilot 等工具提供本地模型后端。
- Prime Agent 在 GitHub 和 YouTube 同时升温。它的 README 强调 Recursive Language Model、Continual Harness、子 agent、持久 Python 控制环境、memory/skill/subagent specs、daemon-backed 运行和 schedules/goals。值得试，但 README 也明确提醒会以用户权限执行模型生成的 Python 和项目命令，因此必须放在隔离仓库和最小权限环境中。
- Augment Intent/Cosmos 代表另一条路径：把多 agent 编排、规格说明、隔离 git workspace、计划审批和 BYOA 组合成开发工作台。这类工具的关键评估点是：spec 是否成为真实状态源、并行 agent 合并冲突如何处理、上下文记忆是否可审计、外部模型接入是否可控。
- OpenAI 的 Codex 使用数据表明，长任务委派已经从内部研发扩展到非开发者组织用户。团队应该尽快把“超过 30 分钟的人类工作”拆成可审核任务模板，并定义什么时候必须人工批准、什么时候允许自动运行。

### 热门应用

- Muse Glimmer：适合想在本地跑 coding agent、处理私有代码、做工具调用和长任务实验的团队。短期不要把它视为云端 frontier model 替代品，而应看作本地 agent runtime 的候选模型。
- Firecrawl：适合有网页、PDF、搜索结果和监控型数据源的 RAG 团队。优先测试 deterministicJson、PII redaction、PDF Inspector 和 monitor，而不是只跑一次性 scrape demo。
- Figma Make / Figma Design Agent：适合已有 Figma 设计系统和变量体系的产品团队。重点不是“能不能生成页面”，而是生成层是否可编辑、变量是否正确、工程侧能否接回代码。
- OpenDesign：适合想在本地文件、代码仓库和设计系统之间做 agentic design 的早期团队。它更像设计/代码协作环境，不适合只追求一个在线 prompt-to-UI demo。
- Prime Agent / OmniRoute / Augment Intent：适合研究长期 coding agent、模型路由和多 agent 编排的开发团队。共同风险是权限、成本、失败恢复和输出可审计性。

### MCP / Agent Skills 更新

> 本轮检查来源：MCP 官方博客、MCP 2026-07-28 specification/changelog、Build with Agent Skills 页面、Skills Over MCP 工作组页面、`mcp-server-dev` 官方插件 README、Agent Skills specification、Cloudflare Agent Skills Discovery RFC、X `skill.md` 文档。未发现 2026-07-28 之后的官方 MCP 协议新版；未发现 `mcp-server-dev` 公开页面新增第四个官方参考 skill。本轮基线仍为 MCP `2026-07-28`。

1. MCP 2026-07-28 协议版本
   - 版本/日期：`2026-07-28`，官方协议基线。
   - 更新内容：核心协议改为 stateless self-contained requests；移除协议级 sessions 和 `Mcp-Session-Id`；移除 `initialize`/`initialized`；每个请求通过 `_meta` 携带 `protocolVersion`、`clientCapabilities`、`clientInfo`；新增 `server/discover` 且 server 必须实现；移除 HTTP GET 和资源 subscribe/unsubscribe，改用 `subscriptions/listen`；所有 result 必须包含 `resultType`。
   - 能力变化：server 可以更容易水平扩展；client/server 能逐请求协商能力；list 类结果可带 deterministic ordering、cache hints、`ttlMs` 和 `cacheScope`；header-based routing 要求 `Mcp-Method`、`Mcp-Name`。
   - 迁移影响：依赖 session、SSE resumability、`ping`、`logging/setLevel`、`notifications/roots/list_changed`、legacy HTTP+SSE 的实现需要调整；Roots、Sampling、Logging 被标记为 deprecated；DCR 也被建议迁向 Client ID Metadata Documents。
   - 适合谁试用：新 MCP server 作者、已有 server 维护者、内部工具平台、需要多实例部署或缓存优化的团队。
   - 行动建议：新项目默认实现 `server/discover`、`resultType`、stateless request 和缓存语义；老项目先做兼容层，再逐步移除 `Mcp-Session-Id` 和初始化握手。
   - 来源：https://modelcontextprotocol.io/specification/2026-07-28 ，https://modelcontextprotocol.io/specification/2026-07-28/changelog

2. MRTR 与安全/授权强化
   - 版本/日期：MCP `2026-07-28`。
   - 更新内容：引入 MRTR，用于 server 需要额外用户信息时的请求路径；OAuth 相关安全要求更明确，authorization server 必须符合 issuer identifier 规则，Client ID Metadata Documents 进入推荐路径。
   - 能力变化：更适合企业级授权和用户身份上下文；工具描述、annotations 和 server 名称继续被视为潜在不可信输入。
   - 迁移影响：工具调用链路要记录用户 consent、数据暴露范围和 tool safety；不能把 server 提供的描述直接当可信策略。
   - 适合谁试用：企业集成、内部权限系统、多租户 MCP 网关、agent 安全团队。
   - 行动建议：把 tool allowlist、用户确认、敏感数据过滤、审计日志作为 MCP server 的默认工程要求。
   - 来源：https://blog.modelcontextprotocol.io/posts/2026-07-28/ ，https://modelcontextprotocol.io/specification/2026-07-28

3. `mcp-server-dev` 官方参考 skills
   - 版本/日期：公开 README 当前列出 3 个 skills；本轮未发现新增第四个 skill。
   - skill 名称：`build-mcp-server`、`build-mcp-app`、`build-mcpb`。
   - 更新内容与用途：`build-mcp-server` 是入口 skill，会先追问 use case、部署方式、工具模式和认证需求；`build-mcp-app` 面向 chat 内 interactive UI widgets，例如表单、选择器、dashboard；`build-mcpb` 面向把本地 stdio server 连同运行时打包，降低用户安装 Node/Python 依赖的门槛。
   - 能力变化：官方推荐从“直接写 server 代码”转为“先识别连接对象、用户、action surface、UI/auth/hosting 需求，再选择 Remote Streamable HTTP、MCP app、MCPB 或本地 stdio prototype”。
   - 迁移影响：已有内部 MCP 脚手架应补齐 discovery、auth、tool design 和 packaging 指南；复杂 UI 不应硬塞进纯文本 tool response，而应考虑 MCP app。
   - 适合谁试用：MCP server/plugin 作者、内部平台团队、想把本地 CLI/API 包装给 agent 使用的开发者。
   - 行动建议：从一个窄能力开始，例如“读取某 SaaS 项目状态”或“生成一个带审批的表单 widget”，再逐步扩展工具面。
   - 来源：https://modelcontextprotocol.io/docs/2026-07-28/develop/build-with-agent-skills ，https://github.com/anthropics/claude-plugins-official/blob/main/plugins/mcp-server-dev/README.md

4. Skills over MCP 工作组
   - 版本/日期：工作组页面当前活动项包含 SEP-2640 Skills Extension、reference implementation、Agent Skills spec coordination 和 Registry `skills.json` proposal。
   - 更新内容：方向是让 skills 可通过 MCP resources / extensions 被发现、分发和消费，而不只是作为本地文件夹存在。
   - 能力变化：如果成形，agent 可以从 MCP server 发现 skill 说明、引用资料和能力边界，降低手动安装/复制 skill 的成本。
   - 迁移影响：内部 skill 目录应尽早保持 `SKILL.md` frontmatter、references、scripts、assets 的清晰结构，并为后续 registry/discovery 准备 digest、schema 和版本信息。
   - 适合谁试用：多 agent 平台、插件市场、企业内部 knowledge tooling、需要在组织内分发工作流的人。
   - 行动建议：不要等待规范完全稳定才整理 skill；先把高频任务写成小而可审计的 `SKILL.md`，并限制权限与外部连接。
   - 来源：https://modelcontextprotocol.io/community/working-groups/skills-over-mcp

5. Agent Skills specification 与公开 discovery 实践
   - 版本/日期：Agent Skills specification 当前强调 `SKILL.md` 必须包含 `name`、`description` frontmatter，支持 `scripts/`、`references/`、`assets/` progressive disclosure；Cloudflare RFC 显示 discovery v0.2.0 使用 `/.well-known/agent-skills/index.json`，并要求 `name`、`type`、`description`、`url`、`digest`。
   - 更新内容：X 文档也提供 `skill.md` 和 well-known discovery 入口，说明公开 API/平台正在尝试让 agent 通过技能说明理解能力边界。
   - 能力变化：skills 不只是 prompt 模板，而是“说明 + 参考 + 脚本 + 资产 + 可发现索引”的组合。
   - 迁移影响：第三方 skill 集合不能冒充 MCP 官方更新；采用时要分清 official MCP core、官方参考插件、社区/厂商 skill discovery 三类来源。
   - 适合谁试用：API 平台、开发者工具、内部自动化团队。
   - 行动建议：为内部工具建立 `/.well-known/agent-skills/index.json` 试验目录时，保留 digest 和版本字段，避免 agent 拉取未验证内容。
   - 来源：https://github.com/agentskills/agentskills/blob/main/docs/specification.mdx ，https://github.com/cloudflare/agent-skills-discovery-rfc ，https://docs.x.com/tools/skill-md

## 今天值得深入研究的 1 个主题

**本地 open-weight agent 与云端 coding agent 的组合边界。**

建议用 Muse Glimmer、Prime Agent、OmniRoute、Firecrawl 和一个真实但低风险的代码仓库做小实验：本地模型负责代码导航、初稿、低敏任务和离线工具调用；云端 frontier model 负责架构判断、复杂修复和最终 review；Firecrawl/代码图谱负责上下文摄取；OmniRoute 或同类 gateway 负责模型切换和成本控制。评估指标不要只看“能不能跑”，而要看任务成功率、权限暴露、失败恢复、token/推理成本、日志可审计性和人类 review 成本。
