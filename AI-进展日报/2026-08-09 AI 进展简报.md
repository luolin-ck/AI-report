## 分领域进展

### 设计生成

- **Claude Design：从 artifact 走向设计工作台。** Claude Design 官方页面将其定位为通过自然语言生成界面、应用、图表和文档的设计环境；相关 YouTube 教程热度说明用户关心的已经是完整 workflow，而不是单次 demo。值得试：产品经理或设计师快速生成多版 UI/UX 方案，然后交给设计系统或前端工程做二次约束。不足：公开页面无法提供精确活跃用户或转化数据，本报告只采用官方功能描述和 YouTube 可见播放量口径。
- **Figma / Claude / Codex 混合流：设计到代码正在变成多工具流水线。** 近期教程多围绕“Claude 生成界面/文案，Figma 做视觉结构，Codex/Claude Code 做工程化”展开。值得关注：这类流程能缩短探索时间，但如果缺少 design tokens、组件变体和响应式状态，很容易产生只适合 demo 的 UI。行动建议：把“组件名、状态、约束、交互、异常态”列为设计生成验收标准。
- **OpenDesign 类项目要谨慎看待 star 叙事。** 公开搜索结果中同时存在已归档/转向的 OpenDesign 页面、AI design generator 站点和开源项目讨论，名称并不总是指同一个产品。行动建议：引用 OpenDesign 时必须给出具体仓库或产品 URL，不要把不同项目的 star、用户数和能力混写。

### 数据采集 / RAG

- **Firecrawl /search：搜索结果质量与动作能力更重要。** Firecrawl changelog 近期持续围绕搜索、抓取、动态页面和结构化内容做更新，适合需要“先搜、再抓、再抽取”的 agent/RAG 流程。行动建议：把 Firecrawl 作为网页和搜索入口，但对关键字段保留二次校验；对需要登录、JS 渲染、PDF 的来源单独记录失败率。
- **pdf-inspector：PDF 不再只是 OCR 问题。** `firecrawl/pdf-inspector` 主打将 PDF 本地解析为结构化 Markdown，适合技术文档、白皮书、合同、研究论文进入 RAG。热度依据：GitHub 仓库页和 Firecrawl 官方 YouTube 视频；未声称独立精确 star 增量。行动建议：用它测试复杂表格、页眉页脚、脚注和跨页段落，避免把“文本抽出来”误认为“语义结构正确”。
- **RAG 采集的下一步是增量监控。** 最近工具链不再满足一次性 crawl，而是在比拼 monitor、freshness、去重和来源可信度。行动建议：为知识库建立 source freshness 字段，超过 7-30 天未更新的网页/PDF 自动降权。

### Agent 工作流

- **Muse Code、Prime Agent、Claude Code、Codex 共同推动“长时 coding agent”成为主战场。** Muse Code 强调成本，Prime Agent 强调 self-improving RLM/coding workflows，Claude Code 和 Codex 强调工具调用与工程上下文。行动建议：测试维度应包含单任务成功率、回滚能力、跨文件一致性、测试执行、token 成本、权限提示次数。
- **Agent skills 正在成为可复用单位。** `addyosmani/agent-skills`、`mattpocock/skills`、`obra/superpowers` 的 Trending 表现说明，开发者把经验沉淀为 skills / recipes / workflow，比单条 prompt 更易传播。行动建议：把团队内部常用 agent 流程写成版本化 skill，附带输入、输出、失败条件和权限说明。
- **安全默认值仍然关键。** 当 agent 能跑命令、改文件、抓网页、登录系统，风险来自 prompt injection、凭据泄露、越权操作和不可审计动作。行动建议：生产环境 agent 必须启用审批、日志、隔离运行和最小权限；`--dangerously-skip-permissions` 类模式只应用在临时沙箱。

## 今天值得深入研究的 1 个主题

**主题：把 agent skills 当作团队工程资产，而不是个人 prompt 收藏。**

建议研究路径：

1. 选 3 个高频场景：代码审查、RAG 数据采集、UI 原型生成。
2. 为每个场景写成 skill：目标、输入、输出、可调用工具、禁止事项、失败回退、验收标准。
3. 用同一个任务在 Codex、Claude Code、ChatGPT、Prime Agent 上跑，记录成功率、交互次数、token 成本、是否误操作、是否能恢复。
4. 将 skill 放进版本管理，像代码一样做 review。不要只在聊天记录里保存 prompt。

这比盲目追新模型更有复利，因为模型会换，但 workflow、权限边界、数据质量和验收标准会留在团队里。
