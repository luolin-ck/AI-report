## 分领域进展

### 设计生成

Figma 的设计生成主线仍然清晰：让 AI 生成物进入可编辑画布，并尽量保留变量、Auto Layout 和与 CSS 更接近的布局语义。[Release notes](https://www.figma.com/release-notes/) 显示，2026-07-24 的 auto layout 更新减少了交付到 CSS 时的差异；2026-07-16 的 code-backed screens 更新让 Make preview、Figma MCP 生成设计和 Chrome extension live capture 回到画布时绑定颜色、字体和 spacing 变量。对产品团队来说，这比“漂亮首屏”更重要，因为它决定生成结果能不能进入真实设计系统。

[GPT-5.6 in Figma Make](https://www.figma.com/blog/gpt-5-6-is-now-available-in-figma-make/) 是近两周设计生成最具体的模型更新。Figma 官方说 GPT-5.6 提升 first pass 质量和迭代速度，覆盖 rough sketch、polished prototype 和 production code。建议用三类任务评估：复杂表单/设置页、移动端响应式页面、设计 token 回流到代码；如果只测 landing page，很容易高估能力。

[Claude Design](https://support.claude.com/en/articles/14604416-get-started-with-claude-design) 仍在 beta，支持通过对话创建 designs、interactive prototypes、presentations，并可使用组织 design system。它适合创始人、PM、运营和前端快速做视觉草稿，但交付质量取决于 design system 是否完整、提示是否具体、输出是否经过真实浏览器和移动端检查。

[OpenDesign](https://github.com/manalkaff/opendesign) 代表开源/本地优先路线：把设计 taste、structured intake、verifier、design-system extraction 写成可安装到 Claude Code、Cursor、Codex、Gemini CLI、OpenCode 的 skills。它适合重视本地仓库上下文、可读技能和可 fork 工作流的团队；采用前要核对安装方式、许可证、真实导出质量和是否会产生难以维护的 HTML/CSS。

值得关注的新变化是 [pbakaus/impeccable](https://github.com/pbakaus/impeccable) 今天进入 GitHub Trending，页面描述为“让 AI harness 更擅长设计的 design language”。这说明开发者社区正在尝试把设计质量写成 agent 可执行的规范，而不是只靠“更好看”这类主观要求。适合设计系统负责人和 coding agent 用户研究：如何把视觉层级、密度、对比、响应式和可访问性变成可检查规则。

### 数据采集 / RAG

Firecrawl 是本周数据采集/RAG 方向最值得跟的产品线。[`/search` 更新](https://www.firecrawl.dev/changelog)强调自定义 relevance model 会对段落、列表、表格打分，只返回最相关 excerpts；官方声称使用 `/search` 的 agents 在 SimpleQA 达到 94.7%，并减少约 10 倍 token。可行动结论：研究 agent 不应默认读完整网页，应先拿可引用片段，再按需要抓取全文。

[Web-scale `/monitor`](https://www.firecrawl.dev/changelog) 也继续值得纳入知识系统。它把查询、目标、去重、过滤和 webhook/email alert 组合起来，适合监控竞品页面、政策公告、开源 release、价格变更和招聘页。建议把 monitor 结果写入结构化表：`url`、`query`、`goal`、`matched_excerpt`、`first_seen_at`、`source_snapshot`、`alert_reason`，方便复核和重跑。

Firecrawl 6 月以来的 Research Index、keyless endpoints、automatic PII redaction、`deterministicJson`、video discovery、`/parse`、Lockdown Mode 和 Highlights/Question format 都指向同一趋势：RAG 入口正在变成“可引用、可压缩、可治理、可复查”的证据系统。对内部知识库和网页抓取团队而言，下一步不是堆更多爬虫，而是评估召回率、片段相关性、引用可追踪性、反爬失败率、隐私处理和成本。

### Agent 工作流

OpenAI Presence 是企业 agent 产品化的参考样本。它把具体 job、最小必要系统访问、公司 policy、approved actions、approval、escalation、simulations、graders 和 Codex-powered improvement process 放在同一个框架中。值得注意的是，Presence 不是自助 API，而是 limited GA，由 OpenAI FDE 和集成伙伴部署，说明高价值 agent 仍然需要流程设计、数据接入和质量运营。

ChatGPT Work/Codex 的 desktop voice 也开始进入工作流层。[OpenAI Help](https://help.openai.com/en/articles/20001275-chatgpt-work-and-codex) 说明 Voice 可在桌面端 Work 或 Codex 中自然打断、协调任务、使用选定体验可用的工具和权限；[OpenAI 社区公告](https://community.openai.com/t/chatgpt-voice-is-now-in-the-desktop-app/1388031)称它可用语音控制多 agent。建议关注点不是“语音好不好玩”，而是它是否降低了用户监督多个 agent 的成本，以及语音指令如何进入审计日志。

GitHub 过去几天的 Copilot 更新密集：[Claude Opus 5 in Copilot](https://github.blog/changelog/2026-07-24-claude-opus-5-is-now-available-in-github-copilot/)、[Copilot cloud agent for Linear GA](https://github.blog/changelog/)、[GitHub MCP Server supports next MCP specification](https://github.blog/changelog/) 和 agent automation controls in Issues public preview 都说明 agent 正在进入 issue、Linear、mobile、IDE、CLI 和代码审查链路。团队评估 coding agent 时，要把 MCP server 权限、CI、PR 审查、依赖更新、成本池和使用指标一起纳入。

### 热门应用

[Health in ChatGPT](https://openai.com/index/health-in-chatgpt/) 是今天最值得关注的消费级 AI 应用之一。它能把健康数据、医疗记录和对话结合起来，用于理解 lab results、跟踪变化、准备就诊问题和健康习惯分析。它不适合替代诊断或治疗；真正值得复盘的是 OpenAI 如何在高敏感数据场景中设计权限、隔离、隐私和专业边界。

[PromptQL](https://www.producthunt.com/products/promptql) 本周在 Product Hunt 页面显示 #2 day rank、470 points、1.2K followers，定位为“multiplayer AI that replaces Slack”。它的核心是共享 AI thread、团队纠错、连接数据库/SaaS/coding agents/events，并沉淀“shared brain”。适合 AI 产品、数据团队和远程协作团队研究，但要重点审查多用户权限、数据连接、上下文保留和误用责任。

[AgentLoop](https://www.producthunt.com/products/agentloop-2) 页面显示 #19 day rank、106 points，定位为每个 cycle 启动 fresh Codex worker 和 critic，通过 GUIDELINES.md/rubric、local sandbox、dashboard、MCP 形成可观察循环。它的价值在于减轻“人在 ChatGPT 和 Codex 之间来回转述”的负担；风险在于 critic 的判断仍取决于 rubric，且大范围文件修改需要 git diff、测试和人工复核。

[Caw](https://www.producthunt.com/products/caw) 是开源 web terminal multiplexer for AI agents，面向 OpenCode、Claude Code、Codex、Copilot、Antigravity、Pi 等 CLI，提供文件浏览/编辑、agent 看板、push notification、worktrees 和 voice mode。它反映了多 agent 使用者的实际痛点：不是没有 agent，而是不知道哪个卡住了、哪个需要输入、哪个已经改完。值得试，但要审查终端访问、本地/远程边界、push notification 数据和冲突处理。

### 模型 / 平台更新

Anthropic Opus 5 的核心信号不是单一 benchmark，而是“默认可用的强 agent model”。官方强调它在 coding、knowledge work、OSWorld、AutomationBench、visual outputs、long-running work、工具变更和 fallback 上更适合日常高强度任务。对企业而言，关键问题是：它是否比更贵的 frontier 模型在成本、稳定性、拒答、速度和审计上更可控。

OpenAI 过去一周的 Health、Presence、Work/Codex Voice 和 long-horizon safety 形成了应用层组合：个人场景走向高敏数据，企业场景走向流程治理，桌面端走向多 agent 操作，安全侧强调长时程轨迹监控。它说明模型公司正在从模型 API 进入垂直产品和工作流操作系统。

GitHub/Microsoft 的更新说明 Copilot 正在变成多模型、多入口、多 agent 控制平台。Claude Opus 5、Gemini 3.6 Flash、MAI-Code、GPT 系列和 Kimi Code 进入同一选择器后，开发者真正需要的是模型选择策略：什么时候用便宜快模型，什么时候用强推理模型，什么时候 fallback，什么时候强制人工审查。

开放权重政策争论会影响模型平台路线。对应用开发者来说，开放模型不是“免费替代闭源”这么简单，而是和数据驻留、推理成本、供应商议价、监管、可审计性、模型来源、许可证、蒸馏争议绑定。建议维护一份模型风险表，把能力、成本、隐私、许可证、来源、部署方式和出口/地区限制分开评估。

## 今天值得深入研究的 1 个主题

**Agent 控制面：从更强模型转向可监督、可回滚、可协作的工作台。**

Opus 5、GPT-5.6、Kimi K3 让 agent 更能干，但今天真正升温的是控制面：Presence 的政策/guardrails/升级规则，ChatGPT Voice 对 Work/Codex 的语音协调，GitHub Copilot 的 cloud agent/Issues/Linear/MCP，AgentLoop 的 worker + critic，Caw 的多终端看板，PromptQL 的共享上下文。结论是：未来半年，agent 产品的差异不只在模型，而在谁能更好地处理上下文、权限、日志、冲突、回滚和人类接管。

建议本周做一个小型基准：选一个真实仓库，设计 5 个任务，分别包含 bug fix、UI polish、依赖升级、文档更新和网页资料收集。让 Codex/Claude Code/Copilot cloud agent 在相同约束下执行，并记录每个系统的输入上下文、命令、文件变更、测试结果、人工打断、错误恢复和最终 diff。最后比较的不是“谁写得像人”，而是谁更容易被监督、复盘和安全接入生产流程。

## 可忽略的噪音

“某模型完全替代所有闭源模型”的标题需要降噪。Kimi、Qwen、Mistral 等开放模型值得测试，但真实替换要看质量、上下文、延迟、工具调用、数据边界、许可证、支持和总成本。

“AI 设计工具一键替代设计团队”的说法仍然过度。今天真正可靠的趋势是变量、Auto Layout、设计系统、代码回流和可编辑画布，而不是一次性生成截图。

Product Hunt points、GitHub Trending stars today、YouTube views、X 第三方抓取都只能作为发现线索，不应直接当成采购、投资或迁移依据。本简报已尽量标注统计窗口和口径限制。

健康类 AI 内容不要按普通效率工具看待。Health in ChatGPT 能帮助整理和理解信息，但它不是诊断或治疗工具；涉及急症、用药、治疗和重大医疗决策必须交给专业人员。
